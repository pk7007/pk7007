## Selected work

### 01 / AI Finance Controller
**Four sources. One reconciliation trail. No invented transactions.**

[Repository](https://github.com/pk7007/razorpay-buildathon)

Built for the Razorpay AI Buildathon's finance-controller track.

A reconciliation engine that connects payment, settlement, bank and ledger records, identifies mismatches, and maintains unresolved exceptions across runs.

**Engineering details**

- Deterministic and structural transaction matching
- Integer-based financial arithmetic
- Constrained AI-assisted exception resolution
- Persistent exception tracking and replay checks
- Reproducible evaluation on synthetic datasets
- FastAPI, Python and SQLite

**Evaluation evidence**

The repository reports 1.0000 precision and 0.9928 recall across its held-out synthetic evaluation. Those results are not claims about live merchant data.

[Read the implementation and evaluation →](https://github.com/pk7007/razorpay-buildathon#evaluation)

## How I approach engineering

**01. Make the assumptions visible.**  
A convincing dashboard cannot replace sound underlying logic.

**02. Separate experiments from production claims.**  
A passing test, a successful simulation and a working deployment are different kinds of evidence.

**03. Give automation boundaries.**  
Important actions need validation, failure handling and a way to stop safely.

**04. Make the work reproducible.**  
Good documentation should help someone else understand what was built and how to verify it.

**05. Build for the user, not just the demo.**  
A useful product has to account for workflows, edge cases and maintenance.
